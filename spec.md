# Спецификация лабораторной № 2

Статус: в `mcp/ItmoBot.Mcp.csproj` подключены официальный MCP SDK 2.3.0,
.NET Hosting и транспорт `stdio`. Проверены соединение, ping, ошибка неизвестного
метода и завершение при закрытии stdin. Добавлены интерфейсы `IMcpClient` и
`IMcpSession` в Application и клиентский адаптер в Infrastructure, зарегистрированный
в DI. Проверены подключение, разрыв, тайм-аут и отмена. Метод `IMcpSession.DiscoverAsync`
получает описания инструментов с обеими схемами и ресурсов через стандартные
списки MCP, включая пагинацию. Обнаружение проверено на пустом настоящем сервере
и наполненном тестовом MCP-сервере. Подключение и обнаружение теперь выполняются
автоматически после миграций, до запуска polling. Scoped-сервис `McpRuntime`
владеет сессией и каталогом, закрывает соединение при остановке и сохраняет
обычный диалог при отказе MCP. На сервере реализованы `get_schedule` и ресурс
`schedule://current-week`, комплектный источник содержит 28 последовательных
обезличенных дней. Проверены обнаружение, вызов и чтение независимым SDK-клиентом,
включая опубликованную сборку. Для погоды подготовлен HTTP-транспорт Open-Meteo
с тайм-аутами, ограниченными повторами и безопасными ошибками. Реализован
`IWeatherService.GetCurrentWeatherByCityAsync`: разбор геокодирования, фильтрация
страны/области, отдельные NotFound/Ambiguous и проверка погодных полей.
Общий срок сценария ограничен `MCP_TIMEOUT_SECONDS`. `get_weather` опубликован
в MCP со схемами всех вариантов результата. Подготовлена миграция `002_agent_reminders.sql` для
пользователей, действий, подтверждений, напоминаний и аудита. Реализованы контракты
и PostgreSQL-репозитории этих таблиц: владелец изолирован, действия подтверждаются
в транзакциях, повтор создания возвращает прежний reminder. Библиотека agent/
переиспользуется ботом и сервером без циклической зависимости. MCP add_reminder,
HMAC-контекст и клиентский подписанный вызов реализованы. Агентный цикл подключён
к DialogueService: нативные tool calls, две операции MCP, проверка JSON Schema,
перехват напоминания в pending и аудит. Telegram-команды /tools, /timezone, /why
и inline-подтверждения подключены;
текущая модель NVIDIA Nemotron прошла live-smoke через production DI с настоящим MCP
и отдельной тестовой PostgreSQL (15/15 проверок). Telegram-кнопки проверяются отдельно. Текущее приложение
сохраняет функции лабораторной № 1. Отметки выполнения — в [plan.md](plan.md).

## Архитектурные решения

- Продолжаем существующее решение C# / .NET 10, новый бот не создаётся.
- MCP-хост — Telegram-приложение, клиент — его инфраструктурный адаптер.
  Сервер — отдельный консольный проект `mcp/`, запускаемый дочерним процессом
  через `stdio`. В stdout сервера только протокол, диагностика — в stderr.
- Используем официальный C# SDK: `ModelContextProtocol` для сервера с Hosting/DI,
  `ModelContextProtocol.Core` для клиента. Сервер использует `ModelContextProtocol`
  2.3.0 и `Microsoft.Extensions.Hosting` 10.0.0; зависимости зафиксированы в lock-файле.
  Клиент использует `ModelContextProtocol.Core` 2.3.0. Обе стороны оставляют
  SDK согласовать версию протокола. Проверка связи использует `server/discover`
  для 2026-07-28 и новее, `ping` — для прежних версий.
- Схемы и описания обнаруживаются через MCP. Приложение проверяет обязательные
  инструменты, входные и выходные схемы; Telegram-обработчики их не дублируют.
  Реализованная граница обнаружения проверяет имена, URI, дубликаты и наличие
  объектных входной/выходной схем, сохраняет независимую копию JSON. Полная
  проверка схем и соответствия им аргументов/результатов, а также обязательного
  набора трёх инструментов относятся к следующим этапам. Признак `ReadOnlyHint`
  сохраняется как метаданные и сам по себе не даёт разрешения выполнить изменение.
  Каталог собирается целиком в пределах `MCP_TIMEOUT_SECONDS`; частичный результат
  при ошибке не возвращается. Лимиты — 256 элементов каждого вида и 32 продолжения
  пагинации; повтор курсора отклоняется. При отсутствии соответствующей capability
  возвращается пустой список без вызова неподдерживаемого метода.
- `IMcpRuntime` из Application управляет доступностью MCP на срок работы бота.
  Повторная инициализация не запускает второй процесс. Получение сохранённого
  каталога через `GetCatalogAsync` сначала проверяет связь; при разрыве каталог
  становится недоступным, сессия освобождается. Отмена не превращается в обычную
  ошибку, автоматического переподключения нет. При ошибке обнаружения частично
  подготовленная сессия закрывается. Миграции — обязательное условие запуска,
  MCP — необязательная внешняя граница. Пустой каталог допустим на транспортном
  уровне; рабочий сервер сейчас объявляет инструмент и ресурс расписания.
  Агентный цикл уже отклоняет неизвестный/недоступный вызов без вымышленных данных;
  при недоступном каталоге обычный ответ формируется без инструментов.
- OpenRouter Chat Completions: нативные `tools`/`tool_calls`, результаты как
  сообщения `role: tool` с `tool_call_id`. Модель только предлагает действие.
  Ответ без вызова должен иметь проверяемые поля `action: respond|clarify`,
  `text`, `reason` через строгую локальную JSON Schema. Формат провайдера задаётся
  явно: json_schema или json_object, без автоматического ослабления/переключения;
  поддержку сочетания tools и выбранного response_format проверяем при интеграции. Произвольный текст не разбирается regex-командами.
- Модель задаётся конфигурацией; существующее имя модели в примере не является
  доказательством поддержки инструментов. До включения агента проверить заявленные
  параметры провайдера и контрольный вызов. Несовместимость — явная ошибка режима
  инструментов, без имитации MCP или скрытой смены модели.
- Для погоды выбираем Open-Meteo: геокодирование и текущие погодные данные одного
  сервиса. Только фиксированные HTTPS endpoints; параметры пользователя кодируются.
- Операции PostgreSQL остаются за репозиториями. Для времени используем TimeProvider;
  для IANA-зон и переходов — единые данные TZDB через NodaTime на всех ОС.
  Для расписания NodaTime 3.3.3 подключён на обеих сторонах, lock-файлы обновлены.

Реализованные части агентного цикла: app/Application/AgentLoop содержит сценарий,
построение запроса с доверенным временем, строгий разбор action/text/reason,
подготовку напоминания и запись аудита. OpenRouterRequestWriter/ResponseParser
поддерживают tools, tool_calls, tool_call_id и явный response_format json_schema/json_object
со строгой локальной проверкой итоговой JSON Schema.
JsonSchema.Net 9.6.0 проверяет обнаруженные входные/выходные схемы; внешние ссылки
схем запрещены, сетевое получение схем отключено, дубли JSON-полей отклоняются.
MCP SDK остаётся в Infrastructure; приложение оперирует LlmToolCall/McpToolOutput.

Результаты инструментов передаются модели с source/trust и не становятся
инструкциями. Код/URL из данных не исполняется; возможности задаёт локальный
список разрешённых имён, а не ReadOnlyHint. Перед каждым запросом проверяется
бюджет с учётом схем/вызовов/результатов, история сокращается полными парами.
Третий вызов запрещён до MCP и отражается как limit_exceeded. В историю диалога
сохраняется только итоговый текст, в аудит — типизированные аргументы (город,
дата, длина текста/время напоминания), статус, причина и длительность.

Историческая проверка прежней модели Qwen выполнена 02.11.2026 и не прошла:
OpenRouter вернул HTTP 404 как для tools+JSON Schema, так и для базового запроса
без этих параметров. Корректность структуры запроса проверена тестами; доступность
текущей конфигурации провайдера/модели не подтверждена. Публичная проверка
02.11.2026 не нашла qwen/qwen3.8-27b:free в API-каталоге при доступной странице модели;
это не доказывает поддержку tools/response_format. После этой проверки выбрана Gemma
(текущий статус приведён ниже). Ошибка
провайдера не заменяется вымышленным инструментом или ослаблением JSON-контракта.

## Режимы и границы агента

Явные запросы погоды, расписания и напоминаний доступны из всех режимов. Обычные
учебные запросы, перевод и опрос сохраняют поведение первой работы. Цитируемая
фраза внутри задания на перевод не считается разрешением создать напоминание.
Модель получает текущий момент и сохранённую зону, не угадывает зону по городу
или языку. Нехватка данных означает уточнение, а не вымышленный аргумент.

На исходное пользовательское сообщение — максимум два фактических MCP-вызова
инструментов, включая неудачные попытки. Автоматического повтора `tools/call` нет;
повторы безопасных погодных HTTP-чтений выполняются внутри сервера. Обнаружение
при подключении не расходует этот лимит. Для агентного чтения ресурса также
расходуется единица лимита. Предложение сверх лимита не выполняется; пользователь
видит причину остановки. Лимит учитывает несколько tool calls в одном ответе модели.

Вызов модели: до 60 секунд на попытку по существующей конфигурации; весь запрос
ограничен общим сроком ожидания. Для MCP: подключение и вызов до 15 секунд каждый;
погодный HTTP — 5 секунд, до двух попыток только при сетевом сбое, 429 или 5xx,
в пределах MCP-дедлайна. Все операции поддерживают отмену. Значения оформляются
настройками и проверяются при загрузке.

Реализованный HTTP-транспорт настраивается через `WEATHER_HTTP_TIMEOUT_SECONDS`
(1–5, default 5) и `WEATHER_HTTP_MAX_ATTEMPTS` (1–2, default 2); бот передаёт
параметры серверу явно. Каждый GET получает новый request и отдельный тайм-аут,
который действует до завершения чтения тела. Повтор — только при сетевой ошибке,
429 или 5xx, с задержкой 250 мс либо Retry-After до секунды. Если Retry-After
дольше секунды, ранний повтор не выполняется; возвращается source_unavailable.
Тайм-аут и некорректный JSON не повторяются. Отмена вызывающего кода прерывает
HTTP или ожидание повтора и не подменяется ошибкой. Ответ ограничен 1 МиБ и
глубиной JSON 32. Транспорт возвращает копию JSON-объекта или типизированную
ошибку; поля геокодирования/погоды проверяют отдельные парсеры перед созданием моделей.
HTTP-клиент не принимает URL, использует фиксированные HTTPS endpoints и
не следует перенаправлениям. Текст ответа API и исключений в ошибки не включается.
Контракт клиента явно разделяет `SearchLocationsByNameAsync` (поиск мест по имени)
и `GetCurrentWeatherByCoordinatesAsync` (текущая погода по координатам).
Фабрика запросов использует имена `CreateLocationSearchRequest` и
`CreateCurrentWeatherRequest`.

## Контракты инструментов

Все входы — JSON-объекты с указанными обязательными полями и
`additionalProperties: false`. До вызова и на сервере проверяются типы и значения.
Все результаты — объекты `structuredContent`, соответствующие опубликованной
`outputSchema`; дополнительный текстовый блок допустим для совместимости.
Даты — календарные, числа — конечные, строки ограничены схемами.

### get_weather — чтение

Вход: `{ "city": string }`, после обрезки крайних пробелов 1–100 символов.

Успех: `status: ok`, `city`, `country`, `temperature_c`, `weather_code`,
`wind_speed`, `wind_unit`, `observed_at` с явным смещением, `timezone` (IANA),
`source` (фиксированный идентификатор Open-Meteo).

Неоднозначность: `status: ambiguous`, `candidates` — варианты с `city`, `country`,
`country_code`, `admin1`; ответ бота просит уточнить страну/область. Не выбираем
первый результат молча. Название страны в запросе нормализуем и используем для
фильтрации геокодирования; неподдержанное или неоднозначное уточнение отклоняем.
Город не найден: `status: not_found`. Доступные ветки описываются в outputSchema.
Для «нужен ли зонт» используем погодные условия текущего наблюдения,
не выдаём их за прогноз на весь день.

Прикладной сценарий зарегистрирован в DI и опубликован как MCP-инструмент.
WeatherMcpEndpoint проверяет аргументы, WeatherProtocolFormatter формирует
structuredContent и совместимый текстовый блок. NotFound/Ambiguous — штатные
результаты с isError=false; Failure — isError=true со структурированной ошибкой.
McpRequestDispatcher объединяет каталог и маршрутизирует вызовы без замены
обработчиков расписания. `WeatherService` зависит от интерфейсов
HTTP-клиента, парсеров и выбора места, возвращает `WeatherResult`. Синтаксис
уточнения — ровно одна запятая: город и страна/область. Для известных названий
стран и ISO-кодов формируется `countryCode` до геокодирования, ответ фильтруется
повторно. Неоднозначные Georgia/Конго/Корея требуют точного ISO-кода. Прочие
уточнения принимаются только при совпадении с названием страны/области в данных;
иначе возвращается invalid_arguments. Страна по языку не угадывается.
Одинаковые места дедуплицируются по имени, стране, области, координатам и зоне;
разные совпадения не схлопываются в первый результат. Если лимит 100 ответов
не позволяет подтвердить единственность, требуется уточнение.

Парсеры проверяют все кандидаты; повреждённый элемент не пропускается молча,
чтобы не скрыть неоднозначность. Необязательный admin1 может отсутствовать.
Отсутствие results допустимо как документированный пустой ответ, results:null
и повторяющиеся поля — ошибки. Погодные значения и единицы проверяются перед
созданием CurrentWeather; Unix timestamp конвертируется через IANA/TZDB в
DateTimeOffset с фактическим смещением в момент наблюдения. Поддерживается
актуальная таблица WMO Open-Meteo, включая код 97. Неизвестные/пропущенные
обязательные значения дают invalid_external_response без тела API в сообщении.

### get_schedule — чтение

Вход: `{ "date": string }`, строго существующая дата `YYYY-MM-DD`.

Успех: `date`, `timezone`, `lessons`, `source`.
Элемент `lessons`: `start` и `end` в `HH:mm`, `title`, `location`.
`end` позже `start`; название и место — 1–200 символов без управляющих символов.
`lessons: []` означает отсутствие записанных занятий на дату.
Источник — фиксированный JSON-файл из репозитория, минимум две недели без персональных
данных; путь берётся из конфигурации, не от модели. Повреждение/отсутствие источника
является ошибкой, не пустым расписанием.
Реализованный источник — `mcp/Data/schedule.json` (2026-10-12–2026-11-08).
Внешний формат: `days: [{date, lessons}]`, даты уникальны; неизвестные и повторные
поля отклоняются. Путь `SCHEDULE_FILE` настраивается администратором и передаётся
дочернему процессу явно, по умолчанию — `Data/schedule.json` рядом с DLL сервера.
Файл копируется при сборке и публикации. На запрос загружается и проверяется весь
источник, неделя использует один снимок без семи отдельных чтений файла.

### add_reminder — изменение

Вход модели: `{ "text": string, "remind_at": string }`.
`text` после обрезки пробелов — 1–500 символов. `remind_at` — ISO 8601 с явным
смещением или Z и моментом строго в будущем; смещение сверяется с сохранённой
IANA-зоной для этого момента. Владельца, ключ идемпотентности, подпись и ID действия
нельзя передать во входных аргументах модели.

Успех: `reminder_id`, `remind_at` (нормализованное время со смещением),
`timezone` (IANA), `created` (boolean). Повтор подтверждённого действия возвращает
прежний ID и `created: false`; новая строка не создаётся.

### Хранение напоминаний: реализованная схема

Миграция `002_agent_reminders.sql` добавляет пять таблиц:
`agent_users` (Telegram-владелец, nullable timezone до выбора зоны),
`prepared_actions` (параметры, SHA-256 аргументов, состояние, срок подтверждения),
`action_confirmations` (подтверждение конкретного владельца/чата),
`reminders` (сохранённый результат действия) и `agent_audit_events` (события для `/why`).
Подготовка и подтверждение относятся к личному чату: chat_id = owner_id.
Идентичность владельца отделена от conversation_users.chat_id первой лабораторной.

БД обеспечивает уникальность исходного update, подтверждения и reminder на action_id,
связность владельца между действием/подтверждением/напоминанием, конечные timestamps,
размер текста/хеша, допустимые состояния и срок подготовки не более пяти минут.
Индексы поддерживают поиск по владельцу, ожидающим действиям, времени напоминания
и запросу аудита. SQL-команды существующих таблиц диалогов и миграции 001 не изменены.

Четыре репозитория реализованы в agent/Infrastructure/PostgreSql;
их контракты и модели — в agent/Application без SQL/SDK.
Подготовка требует выбранной зоны, совпадающей с параметрами, и будущего времени.
Повтор update возвращает прежнее действие; при другом хеше — action_mismatch.
Новый запрос отменяет прежние pending. Смена зоны также отменяет pending,
повтор сохранения той же зоны их сохраняет. Все изменения сначала блокируют
строку пользователя, затем действия; чтения фильтруются по владельцу и чату.

Подтверждение сохраняет запись и состояние атомарно; чужое действие возвращает
NotFound без раскрытия параметров. Просроченное pending переводится в expired,
при этом возвращается ожидаемый отказ. Подтверждённое действие можно выполнить
после срока согласия, если само время напоминания ещё впереди. Один update
подтверждения нельзя применить к двум действиям. Cancel доступен только для pending.

Выполнение сравнивает переданный хеш с сохранённым и вычисленным из параметров,
проверяет confirmed и будущее время, вставляет reminder и меняет статус на executed
в одной транзакции. Повтор executed возвращает прежний ID с Created=false даже
после времени напоминания. Ошибка/отмена откатывает транзакцию, оставляя возможность
повтора. Хеш вычисляется из нормализованного текста, UTC-момента и IANA-зоны;
точность момента заранее ограничена микросекундами PostgreSQL.

IANA/смещение проверяются через TZDB. Аудит принимает типизированное резюме
(длина текста, время, зона), без полного текста, и возвращает последнюю запись
только указанного владельца/чата. SQL-логи содержат код ошибки без параметров.
MCP add_reminder и проверка HMAC реализованы. ReminderMcpEndpoint проверяет два
аргумента и разбирает служебную _meta через ActionContextMetadata; ReminderToolService
проверяет подпись до обращения к БД, читает действие для подписанного владельца,
проверяет смещение/хеш аргументов и вызывает репозиторий выполнения. Неизвестное или
чужое действие даёт unauthorized без параметров записи. Структурированный результат
формирует ReminderMcpEndpoint; схемы определены в его GetTool.
IMcpSession.ExecuteReminderAsync подписывает действие и проверяет structuredContent
через ReminderResponseMapper, не копируя недоверенный текст ошибки пользователю.
Telegram-подтверждения связаны с этими контрактами: ReminderPromptSender показывает
канонические параметры из БД, CallbackQuery.From задаёт владельца, callback_data
содержит только вид действия/ID. ReminderInteractionHandler и
ReminderConfirmationService проверяют владельца/чат/состояние/срок, затем запускают
подписанный MCP-вызов. После success возвращаются ID/время/зона; при неизвестном
исходе успех не объявляется, кнопка подтверждения остаётся для безопасного повтора.
Очистка inline-кнопок после терминального исхода выполняется best effort.
/timezone отменяет pending при фактической смене зоны; /why показывает безопасный
аудит только своего владельца/чата, /tools формируется из каталога MCP.
Повтор callback/update, конкурентное подтверждение и новый MCP-процесс проверены
на отдельной PostgreSQL. Telegram API в автоматических тестах подменяется.
BotApplication обрабатывает до восьми обычных updates и до двух callback
одновременно. Обычные updates одного чата остаются последовательными, callback
обрабатывается независимо от генерации ответа. Telegram offset продвигается только
через завершённые updates по порядку; повторно полученные updates отфильтровываются.
Ключ HMAC и подписи в таблицах не хранятся.

### Ошибки

Для отказа инструмента — MCP `isError: true` и структурированный объект
`status: error`, `error: { code, message, retryable }`, включённый в outputSchema.
Коды: `invalid_arguments`, `unauthorized`, `action_not_confirmed`, `action_expired`,
`action_cancelled`, `action_mismatch`, `source_unavailable`, `external_timeout`,
`invalid_external_response`, `storage_unavailable`.
Ошибки соединения и самого протокола клиент переводит в AppError. Пользователю
не отправляются stack trace, SQL, URL с секретами или внутренние идентификаторы.

## Ресурс schedule://current-week

Только чтение, MIME `application/json`. Данные: `week_start`, `week_end`,
`timezone`, `days` — ровно семь объектов `date`, `lessons` в формате get_schedule.
Неделя — понедельник–воскресенье по серверной настройке `SCHEDULE_TIMEZONE`
(пример `Europe/Moscow`), а не по зоне напоминаний конкретного пользователя.
Приложение получает ресурс через MCP и отображает источник; ресурс не меняет БД.
Граница недели вычисляется через подменяемый TimeProvider.

## Доверенный контекст и подтверждение

Бот получает owner_id из Telegram `from.id`, chat_id и update_id — из update.
Действия доступны только в личном чате. Callback повторно проверяет отправителя
и владельца; знание ID действия само по себе не разрешает подтверждение.

Приложение и дочерний сервер получают общий случайный ключ для HMAC на срок жизни
соединения через окружение процесса, без аргументов командной строки. Остальные
секреты Telegram/LLM серверу не передаются; он получает только нужную конфигурацию.
Независимый клиент не имеет ключа рабочего процесса и не может подписывать контекст.

Для вызова add_reminder клиент добавляет служебную `_meta` вне аргументов модели:
версию, action_id, owner_id, короткий срок подписи, хеш нормализованных аргументов
и HMAC-SHA256 детерминированного представления этих полей. Модель не видит ключ,
метаданные и внутренние ID. Сервер проверяет подпись, срок, владельца и совпадение
с подготовленным действием в БД. Ключ не хранится в MCP-сессии как единственный
источник состояния: действия и подтверждения хранятся в PostgreSQL; после
перезапуска подтверждённое действие может быть повторено с новой подписью.

Состояния действия:

| Состояние | Допустимый переход |
|---|---|
| pending | confirmed после согласия своего пользователя до expires_at; cancelled при отмене; expired после срока |
| confirmed | executed при атомарном создании напоминания; при сбое остаётся доступным для безопасного повтора |
| executed | Повтор возвращает прежний результат |
| cancelled, expired | Выполнение запрещено |

Перед сохранением pending нормализуем параметры и показываем пользователю текст,
дату, время и IANA-зону. Срок подтверждения — 5 минут от подготовки. При смене
параметров старое pending отменяется, создаётся новое с новым подтверждением;
смена зоны также отменяет ожидающие действия. Техническая подпись живёт 60 секунд
и может обновляться для уже подтверждённого действия; это не продлевает право
пользователя подтвердить просроченное pending.

Для одного исходного update допускаем одно подготовленное действие; уникальность
в БД по (owner_id, chat_id, update_id). Один reminder на action_id — уникальное
ограничение. Подтверждение и выполнение используют транзакции/блокировки строк;
создание reminder и перевод confirmed → executed происходят атомарно на сервере.
Конкурентные запросы получают один результат. При неопределённом исходе сетевого
вызова не сообщаем об успехе без проверки сохранённого результата.

Служебное окружение: MCP_SIGNING_KEY (случайные 32 байта Base64 на соединение),
MCP_POSTGRES_CONNECTION_STRING (из существующих POSTGRES_*). В .env бота новых полей
нет; адаптер передаёт эти значения явно и не наследует Telegram/LLM-секреты.
Самостоятельный MCP без ключа отклоняет запись. Без настроенной БД инструмент
обнаруживается, а разрешённый запрос возвращает storage_unavailable. Общий пул
MCP-процесса освобождается хостом, миграции остаются ответственностью бота.

## Аудит и ошибки агента

Для запроса сохраняем в PostgreSQL время, владельца, выбранное действие,
инструмент, безопасное резюме аргументов, проверку/исполнение, длительность,
краткую причину и идентификатор запроса. Не храним скрытую цепочку рассуждений.
Причину для вызова можно сформировать из проверенного действия; для уточнения
и ответа используем проверенные поля ответа модели.

`/why` не выводит подписи, внутренние ID, системный промпт или чужие данные.
В текстовых логах нет Telegram ID, имени, полного текста запроса и секретов.
Инъекции инструкций в погоде/расписании остаются данными, а не новыми полномочиями.
Неизвестные инструменты, лишние аргументы, неожиданные результаты, исчерпанный
лимит, сбои HTTP/MCP/БД приводят к безопасной ошибке и событию аудита, если БД доступна.

## Упрощение архитектуры (05.11.2026)

Пользовательские сценарии и границы app/agent/mcp сохранены. Запуск проходит
через ApplicationRunner и BotHost; scope, миграции и MCP готовит BotHost.
Application сгруппирован по функциям, карта и актуальная диаграмма — в README.
Удалены внутренние интерфейсы, не имевшие альтернативных реализаций;
для простых операций используются общие Result и Result<T>.
Технические счётчики — числа с проверкой в PreparedLlmRequest/LlmTokenUsage.
Специализированные исходы LLM/погоды, подтверждения,
проверки владельца, транзакции, HMAC и лимиты MCP сохранены. SQL-миграции,
ключи и рабочая БД при рефакторинге не изменялись.


Второе упрощение (05.11.2026): простые VO заменены long/Guid/string/decimal/TimeSpan
с сохранением проверок на входных границах и в моделях. Составные ActionOwner,
ReminderSchedule, UserTimeZone, GeoCoordinates и секретные обёртки сохранены.
Большинство простых результатов использует Result/Result<T>. Удалены внутренние
интерфейсы с единственной реализацией; внешние границы остаются подменяемыми.
Схемы и форматтеры инструментов объединены в соответствующих endpoint-классах,
HTTP-парсинг LLM — в OpenRouterLlmClient, Telegram-форматирование — в одном сервисе.
Один самостоятельный тип по-прежнему занимает один файл. Функциональные требования,
схемы JSON, подтверждения, HMAC, изоляция данных и ограничения агента сохраняются.


Исторический результат первого прогона 06.11.2026: пороги не достигнуты
(4/12 действий, 1/9 аргументов). Изменение инструкции исправило 3 из 8 ошибок
в отдельном повторе. Последующий полный прогон достиг порогов (см. ниже). Подробности

Актуальный статус 06.11.2026 после исправления протокола: 11/12 действий и 8/9
аргументов в полном реальном прогоне, пороги достигнуты. В tool_compatible_json
обязателен native tool_choice=required с MCP-инструментами и локальной функцией
submit_final_reply (строгое завершение respond/clarify без MCP). Невалидные,
смешанные и текстовые псевдовызовы отклоняются; черновик повторно не оформляется.
Поток MCP→модель→итог, права, подтверждения и лимит двух MCP-вызовов сохранены.


Суточная квота OpenRouter: для HTTP 429 анализируются структурированные
metadata.limit_source и заголовки квоты. Подтверждённый суточный лимит даёт
LlmDailyQuotaExceeded, безопасный лог с UTC-сбросом и немедленный отказ без
повторов. Старый ответ без limit_source распознаётся только по полному набору
заголовков free-квоты (50/1000, remaining=0, ближайший сброс в полночь UTC)
при отсутствии указанного upstream-провайдера. Неизвестный/повреждённый ответ
остаётся LlmRateLimited. Текст внешней ошибки не используется для классификации.


## Контекст и обработка updates (07.11.2026)

LlmRequest хранит границу обязательного префикса и длину удаляемой истории.
ContextBuilder передаёт их явно; AgentRequestBuilder сохраняет границы при
добавлении инструкций и MCP-продолжения. При превышении бюджета удаляются
только старые полные пары истории. OpenRouterLlmClient повторяет сокращение
после добавления submit_final_reply; обязательные примеры и текущий вопрос
не удаляются. Если обязательная часть не помещается, возвращается ContextTooLarge.
Фатальный отказ polling отменяет обработчики до освобождения scope.
Итоговый полный прогон: 607/607 тестов в Release с отдельной PostgreSQL;
Docker readiness успешен. Ручная демонстрация Telegram отмечена отдельно в plan.md.
